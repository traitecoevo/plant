# `plant` — architecture guide for agents

This document orients coding agents working in the `plant` R package. Read it
before making changes, especially changes that touch the C++/R boundary.

Two companions sit beside it. [.claude/hazards.md](.claude/hazards.md) numbers the invariants a later edit can break without a test failing at once, each with its reason. [.claude/measurements.md](.claude/measurements.md) says where each baseline lives, what may re-bless it, how a build is validated and how a speed claim is measured. plant keeps no plan document: open work lives on its issue.

`plant` is an extensible framework for modelling **size- and trait-structured
demography, ecology and evolution in simulated forests**. It is an
individual-based model in which plant physiology and demography are mediated by
traits. Plants of multiple species can be grown in isolation, in competing
patches, or in metapopulations under a disturbance regime; these dynamics are
integrated up to metapopulation-level estimates of invasion fitness and
vegetation structure.

The performance-critical core is written in **C++** and accessed from **R**.
Reference: Falster et al. (2016) *Methods in Ecology and Evolution* 7:136–146,
[doi:10.1111/2041-210X.12525](https://doi.org/10.1111/2041-210X.12525).

## 1. The big picture: a two-layer package

```
┌─────────────────────────────────────────────────────────────┐
│  R layer  (R/*.R)                                            │
│  - user-facing constructors, dispatch, hyperparameters       │
│  - run() over both solvers and single plants -> plant_run    │
│  - tidy outputs, plotting, utilities                         │
└───────────────────────────▲─────────────────────────────────┘
                            │   RcppR6 + Rcpp generated bindings
┌───────────────────────────▼─────────────────────────────────┐
│  C++ core  (inst/include/plant/**/*.h  +  src/*.cpp)         │
│  - templated class hierarchy: Model, Environment,            │
│    Individual, Node, Species, Patch,                         │
│    DeterministicPatchRunner, Stochastic*                     │
│  - numerics: ODE solver, adaptive quadrature, interpolators  │
└─────────────────────────────────────────────────────────────┘
```

The two layers are bridged by **[RcppR6](https://github.com/richfitz/RcppR6)**
on top of **Rcpp**. The single source of truth for the interface is
[inst/RcppR6_classes.yml](inst/RcppR6_classes.yml).

### Critical rule: never hand-edit generated files

These files are generated and carry "do not edit by hand" headers. Editing them
directly will be overwritten and is almost always a mistake:

- [R/RcppR6.R](R/RcppR6.R) and [src/RcppR6.cpp](src/RcppR6.cpp) — generated by `make RcppR6`
- [R/RcppExports.R](R/RcppExports.R) and [src/RcppExports.cpp](src/RcppExports.cpp) — generated by `Rcpp::compileAttributes()`
- [inst/include/plant/RcppR6_pre.hpp](inst/include/plant/RcppR6_pre.hpp), `RcppR6_post.hpp` — generated
- [NAMESPACE](NAMESPACE) and [man/](man/) — generated by roxygen (`devtools::document()`)

To change the interface, edit the **C++ headers** and
[inst/RcppR6_classes.yml](inst/RcppR6_classes.yml), then regenerate (see §6).

## 2. C++ core class hierarchy

All headers live in [inst/include/plant/](inst/include/plant/); implementations
in [src/](src/). Headers are included via `-isystem../inst/include/` (see
[src/Makevars](src/Makevars)).

The core classes are **templated on two type parameters**:

- `T` = a **Model** type (the rules for growth, mortality and reproduction)
- `E` = an **Environment** type (the resource environment the model reads)

```
Model<E>                            the rules a species' plants follow
  └─ concrete: FF16_Model, TF24_Model, K93_Model

Environment                         resource environment (e.g. light profile)
  └─ concrete: FF16_Environment, TF24_Environment, K93_Environment

Individual<T,E>                     one plant: state + rates from its model
Node<T,E>                           a cohort in the method-of-characteristics
Species<T,E>                        all nodes/cohorts of one strategy
Patch<T,E>                          all Species sharing one Environment
DeterministicPatchRunner<T,E>       the deterministic solver (see §3)
Parameters<T,E>                     model configuration (strategies, schedule, …)
Schedule                            the queue of scheduled events: introductions, pulses, harvests, extremes
```

The headers in `inst/include/plant/` are grouped by role: `numerics/` (quadrature, root-finding, finite differences, the value-and-slope pair, and `fp_contract.h`'s floating-point settings), `models/` (the model interface, environments and every concrete model), `community/` (individual, node, species and patch, for both solvers), `solvers/` (the runners, the schedule and events), `disturbances/` (the patch-age regimes) and `gradients/` (the stand census and its reverse-mode helpers). `util.h`, `util_post_rcpp.h`, `control.h` and `parameters.h` stay at the top, beside the generated `RcppR6_*.hpp`, and `inst/include/plant.h` includes them all.

### The `Model` contract

A Model defines how a plant grows, dies, and reproduces. When subclassing
`Model<E>` (see [model.h](inst/include/plant/models/model.h) and FF16 as the
reference), the key overridable surface is:

- `static size_t state_size()` and `static std::vector<std::string> state_names()`
  — **keep these in sync** with the actual state vector (FF16 returns 5:
  `height, mortality, fecundity, area_heartwood, mass_heartwood`).
- `aux_size()` / `aux_names()` — derived/auxiliary outputs.
- `compute_rates(env, vars)` — the ODE right-hand side for one plant.
- `initial_height()` — the height a newborn plant starts at.
- `compute_competition(z, vars)` — the leaf area the plant holds above height `z`, which is how it shades the others.
- `establishment_probability`, `fecundity_dt`, `mortality_dt`.

Every Model carries a `Control` and an `ExtrinsicDrivers` object.

## 3. Two simulation modes

`plant` solves the same model two ways:

1. **Deterministic — the solver by the method of characteristics.** Cohorts (`Node`s) are introduced on a schedule and integrated as characteristic curves of the size-density PDE. Entry point: `DeterministicPatchRunner<T,E>` in C++, [run()](R/run.R) in R. Recording every step for `tidy()` and adaptive schedule refinement are arguments of `run()` (`record = "steps"`, `refine_schedule = TRUE`); the refinement loop itself lives in `DeterministicPatchRunner::refine_schedule()` in C++ (see below).

2. **Stochastic — finite-size population.** Individuals arrive and die as discrete events. `StochasticPatchRunner<T,E>` in C++; in R, `run(p, method = "stochastic")`, whose runner draws its arrivals in continuous time from each species' birth rate when it is built, and which is stepped with the helpers in [R/stochastic.R](R/stochastic.R).

Both share the same `Model`, `Environment`, `Individual`, and `Parameters`. A single plant grown on its own, `run(individual, times = )` or `run(individual, sizes = )`, is neither: it integrates one `Individual` in the light it is given. `grow_to_times()` and `grow_to_sizes()` in [individual_runner.h](inst/include/plant/solvers/individual_runner.h) run odelia's `Solver` on an `IndividualRunner`, the System that pairs the plant with its environment, and are bound as methods of `Individual`; [R/individual.R](R/individual.R) checks the arguments and shapes the result.

### Where the schedule and the control defaults live

Adaptive schedule refinement is `DeterministicPatchRunner::refine_schedule()` in C++: it flags nodes whose error exceeds `schedule_eps`, bisects the interval below each, repeats up to `schedule_nsteps` times, ends on a run of the schedule it leaves (one more run if the last pass bisected), and writes the refined schedule and ODE times back into its `parameters`, so the `Parameters` object stays self-describing. `run()` ([R/run.R](R/run.R)) builds a `DeterministicPatchRunner` from a `scenario` (`p`, `env`, `control`, `events`), runs it and returns a `plant_run`: the scenario as run, whose `p` holds the possibly-refined parameters, the fitness values and event log as copies, and the live `DeterministicPatchRunner` at `$solver`. A scenario holds its environment as a recipe, plain values that `environment_recipe()` reads and `Environment(recipe)` builds from ([R/strategy_support.R](R/strategy_support.R)), so everything in a result but the solver survives `saveRDS()`, and a result read back runs again from its scenario. A setting a run reads from an environment must therefore be in its recipe: for TF24, `TF24_Environment::recipe()` and `set_recipe()` list them, and the drivers are recorded by the two base-class setters, which are the only writers of `extrinsic_drivers`. A new setting missing from the pair is lost on the way through a scenario, with nothing to say so. `tidy()` of a run recorded with `record = "steps"` returns the tidied steps with those values, `p`, `events` and `event_log`. With `collect_refinement_errors` set, `DeterministicPatchRunner::run()` accumulates each node's refinement error on the patch, read back as `solver$patch$refinement_error_by_node`. The fitness values and error signals are computed by `Patch` and read from it (`solver$patch$net_reproduction_ratios`), and the `DeterministicPatchRunner` keeps no copies of them. Each `Node` records its introduction time and the patch density at its birth, so fitness and error calculations do not re-derive them after the run.

The numeric defaults every run uses are set in one place, the C++ `Control()` constructor ([src/control.cpp](src/control.cpp)); `control_accurate()` tightens the ODE and schedule tolerances for a high-accuracy run.

### 3.1 The TF24 leaf model lives in another repo

TF24's leaf gas-exchange and hydraulics sub-model is **not in this repository**. It
is the standalone header-only [`phylloptim`](https://github.com/traitecoevo/phylloptim)
package, reached through `LinkingTo` and a compatibility shim at
[inst/include/plant/models/leaf_model.h](inst/include/plant/models/leaf_model.h) that aliases
`plant::Leaf = phylloptim::Leaf`. Consequences worth
knowing before you go looking for a leaf bug here:

- **Fix leaf physiology in `phylloptim`, not here.** It has its own golden-file
  regression baseline over 288 operating points and its own hazard list; a change
  made here would be invisible to both.
- **The two repos move together.** plant pins phylloptim to a commit in
  `Remotes:` (and an exact version in `LinkingTo`), so bumping that pin is what
  changes results here. Any coupled change
  lands as a pair of PRs, and the plant half is what re-baselines the stand values.
- **The leaf is purely intensive.** Every input is per unit leaf area or an intensive driver — whole-plant allometry (`kmax(h)`, root carbon totals) is reduced *here* and passed in already divided. That includes the ROOT RESISTANCES: `set_physiology` takes a `RootNetwork`, and `TF24_Model` runs `phylloptim::root_network_from_carbon` on `root_carbon_per_leaf_area_` to build it. Passing a network built from absolute carbon compiles fine, quietly weakens the root system by the leaf area, and **the leaf cannot detect it**: the division happens here, not in the leaf.
- **Do not open-code the layer thickness, and do not switch it to the
  environment's `dz`.** `root_network_from_carbon` scales the vertical resistance
  by `dz[i]^2`, per layer since phylloptim 0.9.0. `TF24_Model` hands it
  `phylloptim::layer_thicknesses(z)`, the shared definition, at both of its call
  sites (the rate evaluation reads it as `environment.z_thickness`, computed once
  when the geometry is set). The widths are `TF24_Environment`'s input and `z` is built from them, so
  the differences are those widths to within rounding -- but not bit-exact: on
  the default 1.5 m over 5 layers, layers 3-5 differ from `depth / n` in the last
  bit, so reading `environment.dz` instead would move every TF24 number. Make
  that switch at the next rebaseline (marked TODO at the call site).
- **`nm` is how you diagnose a stale build.** See the `R CMD INSTALL` note in §6 —
  a header-only dependency changing underneath a stale `.o` produces an error that
  names an untouched field accessor.

### 3.2 When you change the R-facing interface — record it for downstream migration

Renaming, removing, or changing the meaning of anything a user calls (functions,
arguments, argument order, `Control`/`Parameters` fields, R6 types) breaks
downstream products (analysis repos, `regnans`, notebooks). Two
obligations whenever you make such a change:

1. **Record an `old -> new` mapping in [NEWS.md](NEWS.md)** under the development version's **"Breaking changes"** subsection. Write it to be *machine-actionable* — explicit `old(...)` -> `new(...)` lines, one per affected symbol, the way the existing NEWS entries are. This section is the single source of truth for migration; agents.md narrates the *why*, NEWS carries the *exactly what changed*. Pure-internal/perf changes go under "Internals & performance" instead and need no migration line.
2. **Downstream migration is a skill, not a manual chase.** The
   **`plant-update-interface` skill** (`.claude/skills/plant-update-interface/`)
   reads NEWS's "Breaking changes" entries and applies them to a product repo
   (locate call sites, propose per-site fixes, rebuild + test, record a baseline
   marker). It does *not* memorise the API — it re-reads NEWS each run — so the
   only thing that keeps it working is keeping NEWS disciplined per (1). To bring
   a product up to date, run that skill *in the product repo*. If you find a
   breaking change with no NEWS mapping, that's a NEWS bug — fix it at the source.

#### How to write a Breaking-changes entry (format the skill can act on)

The migration skill reads these entries mechanically, so the format matters as
much as the prose. Rules:

- **One bullet per change; PR number(s) at the end** in parens, e.g. `(#463)`.
- **State the `old -> new` mapping explicitly**, with the call form, not just the
  name. `run_scm_collect(p, …) -> tidy(run(p, …, record = "steps"))` is
  actionable; "consolidated the run interface" is not.
- **One sub-bullet per affected symbol** when a change touches several:
  ```markdown
  * <one-line what-and-why> (#NNN). Migration:
    * `old_fn(a, b)`            -> `new_fn(a, b, flag = TRUE)`
    * `old_field`               -> `obj$new_field`
    * `helper()` (removed)      -> `<replacement, or "no equivalent">`
  ```
- **Capture side-channels, not just the renamed call.** If callers read a result
  via an attribute, a returned list element, or a follow-up getter, map *that*
  too — a name-only mapping silently drops it. (Real example: `build_schedule()`
  returned its result with `attr(., "offspring_production")`; the faithful
  migration is `res <- run(p, refine_schedule = TRUE); res$scenario$p;
  res$offspring_production` — the parameters-only mapping loses the
  offspring count.)
- **Flag semantic (not mechanical) changes loudly.** A symbol whose *meaning* or
  *default* changed while its name stayed the same (e.g. raw `Control()` now
  means *fast*, not accurate) must say so in words — the skill cannot infer it
  from a grep and will (correctly) escalate it for human review.
- **Argument-order / signature changes** get their own bullet; advise callers to
  switch to named arguments.
- For a larger reorganisation, describe the design it leaves in the section of this guide that covers that code, and keep the migration itself in NEWS.

### How R dispatches across templated C++ types

Because the C++ classes are templated on `<T,E>`, RcppR6 generates **one
explicit instantiation per registered pair** (`FF16`/`FF16_Env`,
`TF24`/`TF24_Env`, `K93`/`K93_Env`). R-side constructors therefore look like:

```r
FF16_Individual <- function(s = FF16_Model()) Individual("FF16", "FF16_Env")(s)
FF16_Parameters <- function(...)                 Parameters("FF16", "FF16_Env")(...)
```

`Individual(...)` / `Parameters(...)` return the correctly-typed generated
constructor. Generic code recovers the type with
`extract_RcppR6_template_types(obj, "Parameters")` and then dispatches
(see `run.plant_scenario` in [run.R](R/run.R)).

### Hyperparameters vs. raw strategy parameters

A `Model` exposes many low-level C++ parameters, held in a nested **`pars`**
sub-object (`FF16_Pars`/`K93_Pars`/`TF24_Pars`) and accessed from R as
`s$pars$lma`, `s$pars$rho`, … (the strategy's top level only carries `control`,
`birth_rate_*`, `is_variable_birth_rate`, `collect_all_auxiliary`). In C++ these
are read as `pars.<name>`; derived/precomputed quantities (e.g. `eta_c`,
`height_0`, `canopy_shape`, the TF24 `Leaf`) stay as plain strategy members set
in `prepare_strategy()`, not in `pars`.

Users normally set a smaller set of ecologically meaningful **traits** (e.g.
LMA, wood density). A **trade-off (hyperpar) function** — a closure
`f(m, s, filter = TRUE)` — translates traits → strategy parameters and encodes
the trade-offs. **It travels with the `Parameters` object**, in `p$hyperpar`
(a `SEXP` field of the C++ struct, held opaquely in an `RObjectHandle`, so it
survives `validate()`, `run()` and the result's `scenario$p`); `param_hyperpar(p)`
reads it and `generate_strategy`, `add_strategies`, `add_mutant`,
`stand_gradient` and `fixed_point_fitness` take that as their default. The
rules:

- `base_parameters(model)` attaches **no** trade-offs: a trait is written
  straight to `pars`, and `generate_strategy()` says so once per session.
  `hyperpar = NULL` is the same identity, chosen explicitly.
- `default_parameters(model)` attaches plant's **frozen testing trade-offs** (`default_hyperpar(model)`, defined in [default_parameters.R](R/default_parameters.R)) and warns that this is a testing set, not a recommended parameterisation. Every test uses it through the `testing_parameters()` helper, so the goldens rest on it: changing the frozen copy means re-blessing them. The *recommended* trade-offs and the species/site parameter sets belong to `fieldtrial`.
- A trait matrix may also name a numeric top-level strategy field (TF24t's
  thermal parameters, TF24f's `k_acclim`); `parameter_table(model)` lists
  every reachable name by group (`trait`, `derived`, `parameter`, `strategy`,
  `control`).

The pipe-friendly, object-first entry points are `generate_strategy(p, traits)`
(→ a list of strategies) and `add_strategies(p, traits, …)` /
`add_mutant(p, traits, …)` (→ a `Parameters` object); `trait_matrix()` builds
the `traits` matrix. The former `strategy_list()` / `expand_parameters()` /
`mutant_parameters()` are deprecated shims; the old exported hyperpar names
(`FF16_hyperpar`, `make_TF24_hyperpar`, `make_hyperpar(type)`, …) are gone,
with the migration in NEWS.

Allometric/size functions (`area_leaf`, `diameter_stem`, the mass cascade) live
only in C++; the R `*_expand_state()` helpers call them via the exported
`FF16/TF24_strategy_expand_allometry()` (`src/strategy_expand.cpp`) rather than
re-deriving the formulas.

## 5. The interface contract: `RcppR6_classes.yml`

[inst/RcppR6_classes.yml](inst/RcppR6_classes.yml) declares, for each exposed
class: its `name_cpp`, constructor signature, `active` bindings (fields/getters,
often named with a trailing `_` for internal/debug fields), `methods`, and —
for templated classes — the `templates:` block listing the concrete
`<T,E>` pairs to instantiate. This file is what makes a C++ class reachable from
R. If a method/field is not in the yml, R cannot see it.

## 6. Build & regeneration workflow

Use the [Makefile](Makefile) targets. The dependency you must internalise:
**changing the C++/R interface requires regeneration before recompiling.**

| Command | What it does |
|---|---|
| `make RcppR6` | Regenerate `R/RcppR6.R` + `src/RcppR6.cpp` from `RcppR6_classes.yml` |
| `make attributes` | `Rcpp::compileAttributes()` → `R/RcppExports.R` + `src/RcppExports.cpp` |
| `make compile` | `pkgbuild::compile_dll()` (no attribute regen) |
| `make full_compile` | compile **and** regenerate RcppExports |
| `make roxygen` | `devtools::document()` → `man/` + `NAMESPACE` |
| `make rebuild` | **The full pipeline:** `clean` → `RcppR6` → `full_compile` → `roxygen` |
| `make test` | `make all` then `devtools::test()` |
| `make test-installed` | run the suite against the plant installed in `R_LIBS`, not this checkout (§8) |
| `make check` / `make build` / `make install` | `R CMD check` / `build` / `INSTALL` |

Practical rules:

- **Edited a header signature, added a method/field, or touched the yml?**
  run `make rebuild` (or at minimum `make RcppR6 && make full_compile && make roxygen`).
- **Edited only `.cpp` implementation (no interface change)?** `make compile` is enough.
- **Edited only R code / roxygen comments?** `make roxygen` (then `devtools::load_all()`).
- During development, `devtools::load_all()` is the fastest way to test changes.

C++ standard is **C++20** (`CXX_STD = CXX20` in [src/Makevars](src/Makevars)).
Requires R ≥ 4.5.0.

### `R CMD INSTALL` does not clean, and a stale `.o` fails in a misleading way

`R CMD INSTALL` recompiles only sources newer than their `.o`, so object files
left in `src/` from an earlier tree get linked as-is. A header-only dependency
changing underneath them — anything reached via `LinkingTo` — moves no `.cpp`
timestamp at all, so *nothing* rebuilds.

The failure this produces points nowhere near the cause. Consuming the
standalone `phylloptim` package turned `plant::Leaf` from a class into a
`using`-alias for `phylloptim::Leaf`. A stale `RcppExports.o` still carried the
pre-alias mangling, and the load failed with:

```
symbol not found in flat namespace '__Z13Leaf__d___getN5plant6RcppR66RcppR6INS_4LeafEEE'
```

which names a *field accessor* that was never touched, and reads like a missing
export. The tell is in the mangled names, not the message — compare the two
objects and look at which namespace the template argument sits in:

```sh
nm src/RcppExports.o | grep Leaf__d___get   # ...RcppR6INS_4LeafEEE   -> plant::Leaf
nm src/RcppR6.o      | grep Leaf__d___get   # ...RcppR6IN4leaf4LeafEE -> leaf::Leaf
```

Two objects disagreeing about what a type *is* means one of them is stale.
`rm -f src/*.o src/*.so` (or `make rebuild`, which cleans) and build again. Worth
doing unconditionally after any change to a `LinkingTo` dependency.

## 7. Adding a new model (and its environment)

This is the most cross-cutting change in the package: every templated binding and every R dispatch table names each `<Model, Environment>` pair by hand, and nothing generates the wiring. The **`plant-new-model` skill** (`.claude/skills/plant-new-model/`) lists every file a new model touches and the subclass recipe; the commit that added TF24t (`0b68e62f`) is a worked example of the wiring, from before trade-offs moved onto `Parameters` (#731), so ignore its hyperpar lines. Most new models are a subclass of an existing model, as TF24f, TF24t and TF24w are of TF24, and reuse its `_Pars` and environment.

The shipped models:

- **FF16**: the default model (Falster et al. 2011, 2016, 2018).
- **K93**: Kohyama 1993, a simpler size-structured model, and the smallest complete model to read.
- **TF24**: plant's hydraulic model, whose leaf gas exchange and hydraulics are phylloptim's (§3.1).
- **TF24f**: TF24 with a plastic hydraulic operating point, tracked as an ODE state; a subclass.
- **TF24t**: TF24 with leaf thermal damage and acclimation, as a subclass with four appended states ([tf24t_model.h](inst/include/plant/models/tf24t_model.h)). Its thermal parameters sit at the top level of the strategy, beside `pars`.
- **TF24w**: TF24 with a private root-zone soil column per cohort ([tf24w_model.h](inst/include/plant/models/tf24w_model.h)). A subclass with five water states appended, because `state_size()` is static and a parameter-dependent count is not feasible. Its coupling between cohorts (mixing toward the patch mean, land transfer as crowns grow, die and overlap) is two extra passes in `Patch::compute_rates` guarded by the `HasPrivateWater<T>` concept, so no other model pays for them. Limits, each refused where first seen: birth-date coordinate only, no gradient path, no stochastic patch, at most five soil layers. The pooled limit (large `water_mixing_rate`) reproduces TF24 to the mixing lag and is the validation.

### The model registry — the equations as data

[inst/model-registry.yml](inst/model-registry.yml) records the equations of the size-structured layer plant's models share and (as each model's entries are added) of each model, the parameters those equations read, and the C++ symbol that evaluates or holds each. Documents render their equations from it (`model_registry()`, `registry_equation()`, `registry_values()`), so a page's LaTeX is the registry's. Its header is the schema; it follows phylloptim's registry (traitecoevo/phylloptim#168). The rules:

- **A change to a model's equations, parameters or defaults updates the registry in the same PR.** Nothing checks the LaTeX against the code, so re-read the entry whenever its function changes.
- **It is a record, not a check.** No replicas or probes of the equations. `test-registry.R` checks only that named symbols exist on their class, that every `reads` resolves, and that every bound field is accounted for.
- **No line numbers and no default values in it.** Values are read off the live model.
- **Overstorey's notation.** Where an Overstorey theory page already writes an equation, the entry takes its LaTeX (`overstorey:` names the page).
- **The shared layer is written once.** The quantities every model supplies to it (`g`, `d`, `f`, `S_G`, ...) are `slots`, and a model's equation says which slot it `fills`.
- **What phylloptim computes is linked, never copied.** TF24's leaf traits are parameters carrying `link: 'phylloptim:<id>'` and only the plant member that hands them over; their symbol, units and meaning are read from phylloptim's installed registry. TF24's equations name phylloptim's equations in `reads` the same way. Links resolve against the installed phylloptim, and `test-registry.R` asserts that it is the version `LinkingTo` pins, because phylloptim's ids carry no version. So a phylloptim bump that renames or removes a registry id fails here, and the link is updated in the bump's PR.

### Scientific versioning — bump when the science changes

Each model carries a **scientific version** separate from the package `Version`:
a `static constexpr int scientific_version` on the model class in
[inst/include/plant/models/](inst/include/plant/models/), surfaced to R as
`model_version(type)` / `model_id(type)` (`"FF16@v1"`) via
[src/model_exports.cpp](src/model_exports.cpp) and
[R/strategy_support.R](R/strategy_support.R). Downstream tools (notably
`logpile`, which content-addresses archived simulations) read it to decide when
to re-run: **reruns follow scientific changes, not software releases.**

Rules:

- **Bump `scientific_version`** (in the model header, in the same commit) when
  you change equations or default parameters such that the simulation output
  changes for identical inputs.
- **Do NOT bump** for refactors, performance work, interface renames, or
  serialisation-format changes — the science is unchanged.
- FF16/K93 are scientifically frozen and should rarely move; TF24 and its subclasses change
  often and will bump frequently. Read the current values with `model_id()` rather than trusting this line.
- **TF24f is a compound version.** It is an *approximation* of TF24 that
  inherits TF24's equations/parameters, so its version is
  `"<TF24 version>.<approximation revision>"`. The major
  component auto-tracks `TF24_Model::scientific_version` (a TF24 change
  invalidates TF24f too — the safe direction); bump `approximation_revision`
  (in `tf24f_model.h`) only for changes specific to the fast approximation.
  `model_version()` therefore returns a **string** (`"1"`, `"2.1"`), not an
  integer.
- **TF24t and TF24w are compound versions the same way**: `"<TF24 version>.<thermal revision>"`, bumped through `thermal_revision` in `tf24t_model.h` for a change to the thermal-damage layer, and `"<TF24 version>.<private water revision>"`, bumped through `private_water_revision` in `tf24w_model.h` for a change to the private-water model.
- A bump is deliberate: it invalidates that model's `logpile` cache and forces reruns. The drift-guard test [tests/testthat/test-model-version.R](tests/testthat/test-model-version.R) fails when a default changes without a bump (snapshot of each model's default `pars`/`control`); pure equation changes are not auto-detected and rely on review. **The drift guard skips on CRAN**, so in an invocation that sets that flag a bump has no live gate at all: check it ran before believing one. Adding a new model → add its constant and a dispatch arm in `src/model_exports.cpp`.

## 8. Testing

Every baseline the suite compares against, and what may re-bless it, is listed in [.claude/measurements.md](.claude/measurements.md).

`testthat` tests live in [tests/testthat/](tests/testthat/), roughly one file per component (`test-deterministic-patch-runner.R`, `test-patch.R`, `test-model-ff16.R`, `test-leaf.r`, …). Shared setup is in `helper-plant.R`, and the stands the gradient tests share are in `helper-ff16.R` and `helper-tf24.R`. Regression baselines for FF16 are in `tests/testthat/FF16_reference/` and checked by `test-model-ff16-reference-comparison.R` — if you intentionally change FF16 numerics you may need to regenerate these.

Run the suite with `make test` or `devtools::test()`; a single file with
`devtools::test_active_file()` or `testthat::test_file(...)`.

To test an **installed** plant rather than this checkout (a build against a
bumped odelia or phylloptim, say), run `R_LIBS=<lib> make test-installed`. It
prints where plant was loaded from; read that line, because a missing library
falls back silently to whichever plant is in the default library. The target
exists because each of its settings fails quietly when left out:

- It calls `test_check("plant")` from `tests/`. `test_check` evaluates the tests
  in plant's namespace, where the RcppR6 internals (`Parameters`, `Species`,
  `DeterministicPatchRunner`, ...) live. `test_dir()` uses the global environment and reports about
  ninety "could not find function" errors that look like a broken build, and
  `test_check` run from the package root finds no test files.
- It sets `TESTTHAT_PARALLEL=false`, because the parallel workers do not inherit
  `R_LIBS` and fail with an unrelated-looking `queue$poll` backtrace.
- It sets `NOT_CRAN=true`, without which a set of tests skips, and a summary
  reporter shows a skip no differently from a pass.

The pass count depends on the environment, so compare it with a control run of
the same invocation against a reference build, not with a remembered number.

The suite runs under testthat **edition 3** and is parallelised by file
(`Config/testthat/parallel: true` in `DESCRIPTION`). testthat takes the worker
count from `getOption("Ncpus")` / the `TESTTHAT_CPUS` env var, defaulting to
**2** — set e.g. `Sys.setenv(TESTTHAT_CPUS = "8")` in your `~/.Rprofile` to use
more cores. Parallelism only pays off with an optimised build: run `make`
(compiles with `-O2`) before timing, not a bare `devtools::load_all()`, which
builds unoptimised and is much slower.

CI: [.github/workflows/R-CMD-check.yaml](.github/workflows/R-CMD-check.yaml) and `benchmarks.yml`.

`Config/testthat/start-first` lists the slowest test files, slowest first, so that testthat's file-level workers start them before the short ones. It also sets what a pull request's Windows leg leaves out: CI passes the list, less each model's own file (`model-*`) and `deterministic-patch-runner`, to [tests/testthat.R](tests/testthat.R) as `PLANT_TEST_EXCLUDE`. A push or a manual run checks every file on Windows, and Linux runs every file on every pull request. So a file belongs in the list only if it is slow, and adding one drops it from a pull request's Windows check unless it is one of those kept.

## 11. Conventions & gotchas checklist

The one-line rules. The invariants behind the solver, the reverse sweep, the soil column, the continuous patch and the TF24 variants are numbered, with their reasons, in [.claude/hazards.md](.claude/hazards.md).

- ❌ Do not edit generated files: `R/RcppR6.R`, `R/RcppExports.R`,
  `src/RcppR6.cpp`, `src/RcppExports.cpp`, `RcppR6_pre/post.hpp`, `NAMESPACE`, `man/`.
- ✅ Edit headers in [inst/include/plant/](inst/include/plant/) and the yml; then regenerate.
- ✅ Adding/removing strategy state → update `state_size()` **and** `state_names()`.
- ✅ Exposing a new C++ method/field to R → add it to `RcppR6_classes.yml`, then `make RcppR6`.
- ✅ Adding a model → follow the `plant-new-model` skill's checklist: nothing generates the wiring, and each R `switch()` table, binding and version arm names every model by hand (§7).
- ✅ Changing a model's equations/default parameters (output changes for the
  same inputs) → bump its `scientific_version` in the model header (see §7).
- ✅ After interface changes run the full `make rebuild`; after C++-only changes `make compile`.
- ⚠️ **TF24 and its subclasses run one cost curve, `TF24_floor`, seated once in `TF24_Model::prepare_strategy()`.** phylloptim's collar-solve entry points are templated on the curve, and plant's call sites name `Leaf::CostCurve::TF24_floor` explicitly. Each must name the curve that is seated: one that names another solves that curve while `shadow_cost()` reports the seated curve's price, and nothing errors. To change the curve, change the seat and every `CostCurve::TF24_floor` together (`git grep -n 'CostCurve::'`).
- ⚠️ **TF24's leaf parameters must keep phylloptim's names.** Most are handed to the `Leaf` constructor **positionally**, so a name that disagrees with the slot it lands in is silent, not a compile error: `vcmax_25`, `stem_c`, `stem_P50`, `root_c`, `root_P50`, `TF24_beta2`, `jmax_25`, `phi_J`, `curv_fact_elec_trans`, `curv_fact_colim`, `TF24_cost_scale`. The rest (`R_d_25`, `g_min`, `TF24_floor_lambda_o` and the energy-balance fields) are set on the leaf by name in `construct_leaf()`. Each vulnerability curve reaches phylloptim as its (P50, c) pair, in `construct_leaf()` and in `leaf_pars_on_tape()`, and phylloptim derives the Weibull scale and the critical potential itself. `TF24_Pars`'s `stem_b`, `psi_crit`, `root_b` and `root_psi_crit` are derived copies that nothing reads, so setting one does not change the curve. Only the frozen trade-off updates `stem_b` and `psi_crit`, and nothing updates the root pair, so after P50 or c is set they can still describe the default curve.
- ⚠️ **Never put a non-finite number in an ODE state, and do not read
  `check_finite_ode_state` as protection against one.** It tests the cohort
  density (`exp(log_density)`, so `-Inf` passes as a finite zero) and the
  environment's own states; the slots `Model::state_names()` declares and
  the node's two extras are not looked at. A `+Inf` hazard from `-log(0)` at an
  establishment probability of exactly zero therefore ran for years: every reader
  is guarded (`is_finite` tests, or `exp(-mortality)`, which is zero either way),
  so the forward model is right and silent, while the recorded trajectory the
  reverse sweep replays carries an entry no row can attach to and **every census
  metric comes back not-a-number with no refusal declared** — which the parity
  gate cannot see, because there is nothing to name. Where a sentinel is wanted,
  pick a finite one whose consumers read the same numbers: `establishment_failure_hazard`
  is 750 because `exp(-x)` is exactly zero past 745.14. `test-gradient-parity.R`
  asserts every recorded state is finite on all five drivers.
- ⚠️ **`phylloptim` and `odelia` are pinned with `==` in `LinkingTo`, deliberately.**
  Both are compiled into plant and plant's baselines are bit-exact, so a `>=`
  bound lets a later upstream release change plant's arithmetic with no local
  change to explain the red baseline. Upgrading means bumping the pin *and* the
  `Remotes:` sha together, rebuilding, and recording the baseline diff.
- ℹ️ Active bindings ending in `_` generally expose internal C++ fields for
  inspection/testing, not part of the stable user API.
- ℹ️ Two solvers (deterministic, stochastic) share the same model classes —
  changes to a Model affect both.
- ⚠️ Several hot-path constructs look "wrong" but are deliberate performance
  choices — see §12 before "tidying" them (inline helpers in headers, integer
  index constants, ratio-first signatures, scratch buffers).
- ✅ Opening a PR → its title and body **become the squash commit message**, verbatim
  and permanently. Subject ≤72 chars *including* the ` (#NNN)` GitHub appends, body
  under 20 lines. Measurements, benchmark tables, suite counts, rejected alternatives,
  disproved hypotheses and branch bookkeeping go in the **first PR comment** instead —
  see [`commit-messages.md`](https://github.com/traitecoevo/plant-meta/blob/main/governance/commit-messages.md).

## 12. Performance & optimisation strategies

The deterministic solver spends almost all of its time in one nested loop
(`DeterministicPatchRunner::run` → `ode::derivs` → `Patch::compute_rates` → `Species::compute_rates`
→ `Node::compute_rates`/`growth_rate_gradient` → `Model::compute_rates` →
`assimilation`/competition). Because that loop runs for every node, every
quadrature point, every timestep, small per-call costs dominate. The codebase
uses a consistent set of techniques to keep it fast. **Many of these make the
code look more complicated than the underlying maths — do not "simplify" them
back without re-profiling.** The profiling workflow and the catalogue of
techniques that paid off are captured in the `profile-plant` skill
(`.claude/skills/profile-plant/`); the umbrella issue is [#466], with
follow-up [#470] (LTO).

**Algorithmic (the big wins):**

- **Spline-based competition environment — turns O(n²) into ~O(n).** Naively,
  computing the light each plant experiences means summing the shading of every
  other plant, i.e. O(n²) per timestep for n individuals. Instead
  `Patch::compute_environment()` builds a *resource spline*
  ([resource_spline.h](inst/include/plant/models/resource_spline.h)) **once** per
  timestep by evaluating cumulative competition at a fixed set of heights; each
  individual then queries the environment with an O(1) spline lookup
  (`get_environment_at_height`). Cost becomes O(n) to build + O(1) per query.
- **O(1) spline lookup.** odelia's `hermite_spline` (`odelia/spline.hpp`)
  checks in `set_nodes()` whether its knots are equally spaced. If they are, it
  finds a point's span by arithmetic instead of a binary search; if not, it
  guesses from the mean spacing and steps to the right span. ([#435])
- **Finite-difference gradient: a copy, and deliberately not a scratch.**
  `Individual::growth_rate_gradient()`
  ([individual.h](inst/include/plant/community/individual.h)) needs a mutable `Individual` to
  perturb height on, and copy-constructs one per call. A `thread_local` scratch was
  tried and removed: three arrangements measured within 1.5%, and the function has
  since moved to `Individual` and become scalar-templated, so a cached scratch would
  exist at the active type and carry tape slots across recordings — the aliasing
  failure `deterministic_patch_runner.h` records, for 1.5%. **Do not reintroduce it.** The copy is also
  absent from the gradient path entirely: `log_density_rate` calls this only on the
  height coordinate, and the reverse pass runs on the birth-date one.
- **Stand gradient: forward walks for a few columns, the sweep for many.** `census_trait_gradient` sweeps back over the recorded steps once per metric, at the same cost whatever the number of trait columns. `census_trait_gradient_forward` walks forward over the same steps on odelia's `tangent_lanes<W>`, one column per lane and up to eight a walk, at about a replay plus a share per lane and whatever the number of metrics. `stand_gradient(mode = "auto")` picks by column count (`forward_gradient_crossover` in [R/stand_gradient.R](R/stand_gradient.R), with the measurement it rests on). The forward walk is compiled only for a strategy that keeps no inner solve's choices (`walks_forward`), which is FF16 among the census models: TF24's walk would solve the leaf again at the lane scalar rather than replay what the run chose. Both routes must keep the same requirements and refusals, so a gate added to one is added to the other.

**Templated headers & inlining (this build has _no_ LTO).** `src/Makevars` uses
`CXX_STD = CXX20` with no `-flto` and `DESCRIPTION` has no `UseLTO`, so a
function defined in a `.cpp` translation unit **cannot** be inlined into the
templated `Individual<T>`/`Node`/`Species` code instantiated in another TU.
Every such call is a real, non-inlinable call on the hot path. Consequences you
will see in the code:

- Small, hot strategy helpers are **defined inline in the header**, not in the
  `.cpp`: `area_leaf`, `update_dependent_aux`, the `compute_competition`
  overloads, and `compute_competition_by_ratio` live in
  [ff16_model.h](inst/include/plant/models/ff16_model.h) and, for TF24,
  in [tf24_model.h](inst/include/plant/models/tf24_model.h) and the headers it
  includes (`tf24_allometry.h`, `tf24_rates.h`); `util::is_finite`
  and the `Interpolator` accessors are inline in their headers. Moving them back
  into a `.cpp` re-introduces a cross-TU call and measurably slows the loop.
- The cleanest fix for the remaining large cross-TU calls (`assimilation`,
  `compute_rates`) is enabling LTO — tracked separately in [#470] because it is
  a build-config change with toolchain/portability trade-offs.

**Avoiding repeated per-call overhead:**

- **Integer index slots instead of string-map lookups.** State/aux/rate access
  in the hot path uses fixed integer constants (`HEIGHT_INDEX`,
  `MORTALITY_INDEX`, `*_AUX_INDEX` `constexpr`s in the model headers, and the
  cached `*_aux_index` members in [individual.h](inst/include/plant/community/individual.h))
  rather than `std::map<std::string,int>::at("name")`. **These constants must
  stay in sync with the order of `state_names()`/`aux_names()`** — there are
  comments saying so at each declaration. Named string access is kept for the
  R-facing/diagnostic paths.
- **Cached dependent auxiliary state.** Values that depend only on height are
  computed once when height is set (`update_dependent_aux`) and stored in aux
  slots: `competition_effect` (= `area_leaf(height)`) and `height_inverse`
  (= `1/height`). The competition and assimilation paths read these instead of
  recomputing `area_leaf` and the division every call.
- **Eta-specialised canopy shape.** [canopy_shape.h](inst/include/plant/models/canopy_shape.h)
  (`CanopyShape`, shared by FF16/TF24/K93) selects a multiplication-chain
  implementation of `u^eta` *once* in `prepare_strategy()` for common integer
  `eta` (1,2,4,8,10,12), avoiding the libm `pow()` slow path per quadrature
  point; also caches `1/eta`. ([#465], libm `pow` cost from [#361])
- **Ratio-first signatures.** `q()`/`Q()` and the competition helpers take the
  height-normalised ratio `u = z/H` (plus a cached `1/height`) directly, so the
  `z/H` division is hoisted out of inner loops rather than repeated per point.
- **No `std::function` in quadrature.** `assimilation()` passes its integrand
  lambda to the templated `QK::integrate` by its own closure type, **not**
  wrapped in `std::function`, so the integrand inlines at each quadrature point
  instead of making a type-erased indirect call.
- **Hoisting loop invariants.** The light-spline upper bound (`canopy top`) is
  fetched once per `assimilation()` call and passed into the capped
  `get_environment_at_height(z, cap)` overload, instead of re-reading
  `spline.max()` per quadrature point; within the crown integral the bounds are
  already guaranteed, so the *unchecked* `spline(height)` is used in place of
  `spline.eval()`.
- **De-duplicated math kernels.** Where two allocation-derivative terms share a
  `pow(area_leaf, a_l2)`, it is computed once (see
  `FF16_Model::darea_leaf_dmass_live`).

**Measuring.** Benchmark an installed build (`R CMD INSTALL`), not `devtools::load_all()`, which compiles with different flags. What counts as evidence of a speed change, and why wall-clock alone does not, is in [.claude/measurements.md](.claude/measurements.md); the profiling workflow is the `profile-plant` skill. `run_plant_benchmarks()` times FF16 only. A speed change must leave the baselines bit-identical unless a moved number was agreed in advance.

## 13. Writing a model that carries an active scalar

A model is templated on the scalar `S` it carries: its state, its traits and
everything derived from them. `double` is production; an active `S` records the
computation so a derivative can be taken from it. Write the science once. If new
physiology does not compile at the active scalar, that is the design working —
it is telling you the quantity you just wrote is not differentiable the way you
wrote it, and the rules below are the reasons why.

**Fractions are `double`; positions and values carry `S`.** A knot fraction, a
quadrature abscissa as a fraction of an interval and a sort key are decided on
passive values, and declaring them `double` says so. The *position* built from
one is not: a crown abscissa is `height · ξ`, and reading the field at the
fraction rather than at the position makes `d/d(height)` exactly zero. A knot
*count* that depends on an active value makes the recorded computation depend on
the state.

**Declare an inner solve by its residual**, through `implicit_value`. Never
differentiate the iteration that found the root: a golden-section result is
affine in its bracket and independent of the objective's values, so recording
the search returns the bracket's derivative.

**Never define a rate as a numerical derivative of an active quantity.** If a
rate is a difference, difference on a grid the model already has.

**A clamp, floor, `min`/`max` or `if` on a computed value is a derivative
decision.** Record it with the incidence that justifies it.

**Never give a deduced return type to anything returning an active value.** The
AD operators return expression templates holding references to their operands,
so a deduced return type hands the caller references to temporaries that die on
return; the reverse sweep then reads reused stack memory and segfaults
arbitrarily far from the cause, invisibly to valgrind. Declare the scalar return
type on every such function and lambda, including one-line helpers:

```cpp
// BAD  -- returns a dangling expression template
auto anchor = [](double v, S x) { return S(v) + (x - to_passive(x)); };
// GOOD -- the same arithmetic, materialised while its operands are alive
auto anchor = [](double v, const S& x) -> S { return S(v) + (x - to_passive(x)); };
```

The two differ only in `-> S` and taking `x` by reference. That is the whole
lesson: the fix is the declared return type.

**A supplied derivative cannot be checked against the value it is attached to.**
Where a submodel hands back constants and its partials are attached by hand, the
recorded expression is `value + Σ partial_i * (x_i - to_passive(x_i))`: exact in
the derivative and **identically zero in the value**, by construction. So a finite
difference of that function is zero on every supplied input whether the
partials are there, wrong, or silently dropped — and dropping them gives a
gradient column of exactly zero, which reads as an answer. Two rules follow.
Build the input vector from the submodel's own `inputs()`, name-driven,
with a hard stop on a name you cannot map, so a widened boundary is a compile or
run failure rather than a shorter vector. And never `resize` a partials row to
fit the inputs you happened to build: check the length and fail.

**Two arguments of one type with unrelated meanings is a silent-swap hazard**,
the more so under templating, because a template argument makes both of them the
same type wherever it is instantiated. Prefer a named struct or distinct types;
where you cannot, the call sites are a review checklist rather than a compiler's
problem.

### Adding a census metric

A census metric is a weighted reduction over the size distribution: the trapezium integral of `n_k * psi(state_k)` over the cohort birth dates, with `n_k = exp(l_k)`. `Species::census` owns the reduction and `psi` owns the quantity. The metrics travel as a list, so the codomain of a census -- and of its gradient -- is the list's length, and a metric is added without touching the reduction, the reverse pass or `odelia`. Four steps:

1. **Write the metric** as one more entry of the model's `census_metrics()` (TF24's is `census_metrics_for()` in [inst/include/plant/models/tf24_model.h](inst/include/plant/models/tf24_model.h), which TF24f shares; FF16's is in [inst/include/plant/models/ff16_model.h](inst/include/plant/models/ff16_model.h)): a `census_metric<M>` ([inst/include/plant/gradients/census.h](inst/include/plant/gradients/census.h)), a name and a function of the strategy and one cohort's `Internals` returning the scalar. It reads the strategy and one cohort and nothing else; a metric with a height cut of its own applies the cut inside the function. Declare the return type -- the AD operators return expression templates, and a deduced one dangles (above); `census_metric`'s plain function pointer makes that a compile error.
2. **Size the list.** `census_metrics_for()` returns a `std::array` of fixed length, so its count goes up by one. `census()`, `census_state_and_trait_rows()` and `census_trait_gradient()` in [inst/include/plant/solvers/deterministic_patch_runner.h](inst/include/plant/solvers/deterministic_patch_runner.h) read the list, and `census_metric_names(x, model)` reports it, so the new row appears in the value, in the seed and in the gradient with no further edit.
3. **Rebuild**, after `rm -f src/*.o`: the header is inline and R's make does not track header dependencies. No export signature changes and no new symbol reaches R, so `make RcppR6` and `make attributes` have nothing to do.
4. **Assert its value and its gradient rows.** The value against an independent R-side computation from the tidied output, as `test-census.R` does, and the gradient against a pinned-step central difference (`pin_steps()` and `central_difference()` in `tests/testthat/helper-plant.R`) of a trait that genuinely moves it -- a row of exact zeros reads as an answer and is this design's worst failure mode, so name the trait and say why it moves the metric.

What a metric may *not* do: read another cohort, read the light field, or carry a state of its own. Each of those makes it a term in the rates rather than a functional of the state at one time, and the seeding in `DeterministicPatchRunner::census_state_and_trait_rows` — one recording of the reduction with the ODE state as its inputs — would no longer be the whole derivative.

## Independent review of every PR

**When you open a PR, commission one independent review before telling the user it is ready.** Don't ask first; it is part of opening the PR. Commission another after a push that changes the PR's substance (a design revision, a new code path), not after a typo fix. Skip it only for a PR that changes nothing but a version or a typo, and say that you skipped it.

**Reviewer:** Gemini through `/delegate-agy` (`gemini-4-argon-high`, never `flash`, which has invented quoted code) when its quota allows and the skill's data gate passes. Otherwise use a fresh-context Claude subagent (Agent tool, `general-purpose`, in the background). The brief is the same either way.

**Set-up:**

- Make a detached worktree of the PR head in your scratchpad: `git worktree add --detach <scratchpad>/rev-<PR> <branch>`. That way the review cannot touch your branch.
- Give the reviewer a scratch directory of its own for builds and scripts.
- Run it in the background and carry on. Don't also do the review yourself.

**The brief** is the template below. Give the reviewer the code and the PR's claim, not your reasoning or conclusions. Tell it to form its view before reading the PR's first comment, which is your account. It is read-only: no edits, commits, pushes or GitHub comments.

**When it reports:**

1. **Verify every finding against the code before acting.** Read the cited lines, or reproduce the claim. Quotes, line numbers and counts are claims, not facts. Run any numerical claim. For "this test would catch X", show the test fails on the old code.
2. **Fix what holds, on the same branch.** Re-run whatever the fix could affect: goldens, object identity, test suites.
3. **Post one PR comment** with:
   - what the reviewer checked and found clean;
   - each finding you fixed, with the commit;
   - each finding you rejected, and why;
   - any correction to your own earlier comments. Correct the record there, never in a commit message.
4. **Tell the user in plain words:** how many findings, what changed, what you rejected, and anything that needs their decision. A finding that is really a decision about scope, API or modelling goes to the user as an open question, not into a quiet fix.

## Issue & project-board conventions

Development across `plant`, `regnans`, and `overstorey` is tracked on a
shared [project board](https://github.com/orgs/traitecoevo/projects/5). New issues
are auto-added to the board with **no Status** — that's the triage queue. A maintainer
sets Status (e.g. Backlog) during triage, so you don't need to set it yourself.

When opening an issue (including whenever the user asks you to create one), always:

- **Set exactly one type label.** Only three labels exist in these repos — do not
  invent new ones:
  - `bug` — an existing feature not functioning as intended
  - `task` — a discrete task needed for a feature (the default for normal work)
  - `epic` — a new feature or capability, usually an umbrella over several tasks
- **Prefix the title with a theme tag** in square brackets so the board sorts
  cleanly. Reuse an existing theme where it fits; only fall back to `[other]` when
  nothing applies:

  | Tag | Scope |
  |---|---|
  | `[TF24 hydraulics]` | Hydraulics component of the TF24 model |
  | `[TF24 allometry]` | Flexible allometry for the TF24 model |
  | `[TF24 nsc]` | Non-structural carbohydrate storage in TF24 |
  | `[acclimation]` | Acclimation of leaf and other traits |
  | `[simplify interface]` | Consistent interface to the plant & regnans models |
  | `[evol assembly]` | Evolutionary assembly linking plant to regnans |
  | `[Env drivers]` | Driving the model with environmental drivers |
  | `[speed]` | Performance — making the model run faster |
  | `[patch variations]` | Multiple patch setups (multi-patch, stochastic metapopulation, continuous patch) |
  | `[AutoDiff]` | Enabling automatic differentiation in plant (e.g. for gradient-based calibration) |
  | `[forecasting]` | Enabling forecasting with the plant model |
  | `[documentation]` | Documenting model capabilities (any of the three repos) |
  | `[other]` | Anything not covered above |

  A title may carry more than one tag when it genuinely spans themes
  (e.g. `[speed] [TF24 hydraulics] …`).

Create issues with `gh issue create -R traitecoevo/plant --title "[tag] …"
--label task` (swap in `bug`/`epic` as appropriate).


## Writing in this guide

This file is read in full at the start of every agent session, as current
instructions, by a reader who was not in your session and cannot tell which
parts are out of date. When you change it:

- Write what is true now, in the present tense. If something here turns out to

- Give each rule its reason, in plain case. A reason persuades where capitals
  and warning signs do not.
- Point to where a value lives (`DESCRIPTION`, a header, a Makefile target)

  names that already exist in the code.

`plant` is part of the **plant family** in the [`traitecoevo`](https://github.com/traitecoevo)
org — a hub-and-spoke set of packages built around the
[`plant`](https://github.com/traitecoevo/plant) size- and trait-structured forest model.

- **Docs hub** — family user guides & theory: <https://traitecoevo.github.io/overstorey/>
- **Cross-package orientation** — how the family fits together (who depends on whom,
  source-of-truth rules, cross-repo gotchas) lives in
  [`plant-meta`](https://github.com/traitecoevo/plant-meta); start with its
  [`AGENTS.md`](https://github.com/traitecoevo/plant-meta/blob/main/AGENTS.md). Keep
  family-wide concerns there, not here.
- **Issues & board** — follow the
  [issue guide](https://github.com/traitecoevo/plant-meta/blob/main/governance/issue-guide.md);

  `needs-info`, `cross-package`, `breaking`, `question`.
- **Commit messages** — the repo squash-merges, so a PR's title and body are copied verbatim into
  permanent history. Keep them short and durable and put the working detail in the first PR
  comment; the split is set out in
  [`commit-messages.md`](https://github.com/traitecoevo/plant-meta/blob/main/governance/commit-messages.md).
- **What should run vs. what should fail** — strategies and environments are expected to run
  across a wide range of trait values and conditions and give sensible biological outputs
  (including zero growth or reproduction) rather than crash; a *physically unrealistic* state
  should fail, naming the quantity, its value and the constraint violated. Read
  [`model-robustness.md`](https://github.com/traitecoevo/plant-meta/blob/main/governance/model-robustness.md)
  before adding or removing a guard in a strategy, environment or numerical routine — it has the
  decision rule, and the traps (a guard returning a plausible number is worse than a crash; a
  state that can only be *inferred* from the outputs is not disclosed).
